# 73 个 HLP 仓位周期原档复核（2026-11-15）

## 结论与实际修复

52 个原来标记仓位衔接异常的周期，34,437 处差额全部可以由同一 IEEE-754 binary64 数值的十进制表示尾差解释，范围为 1e-10 至 1.2e-8。回查 32 个原始官方压缩文件，逐笔验证目标周期的全部 138,364 条记录，并检查原档窗口中没有提取遗漏。未发现真正漏成交或错序的证据。

修复的是连续性判定及派生仓位表示，不是改写官方原文，也不是找到新的成交。规范化为同一 binary64 数值的最短十进制表示后，以 Decimal 做精确算术，52 个周期均从真实零仓位逐笔严格衔接、严格归零，数量守恒。没有用统一绝对容差把差额忽略掉。每个原始数值及原判断仍保留在原来的43列中，新加7列给出修复值和复核结论。

当前官方 meta 的 szDecimals 网格也全部通过，但它只作辅助检查，不冒充历史精度快照。这里的结论是对已核对记录的数值表示修复，不声称已经证明整个官方归档永无缺失或隐藏的往返交易。

21 个 PnL 缺失周期与上述52个不重合，涉及5,239笔成交。原始 node_trades 记录顶层和 HLP 侧 side_info 都没有 PnL 字段；原提取程序没有漏读。这是字段缺失，**不是这21个周期缺少成交或仓位轨迹断裂**。逐周期调用免费官方 userFillsByTime，aggregateByTime=false，21次均返回空数组。另查两账户从startTime=0开始的可检索记录，返回起点均晚于这些2025年3月至5月的周期；结合官方仅保留最近10000笔的限制，不能把这些空响应解释为历史上没有成交。

同时检查本地三份旧 HLP exit fills JSON 缓存，它们也没有这些早期时间段的记录。官方PnL补回0笔，5,239笔继续留空。没有把自行计算的价格盈亏、对手方PnL或清算accountValue当作官方closedPnl。

## 文件

- `cycle_audit.csv`：73个周期，每个一行，包含开始/退出时间、原问题、差异数量、最大差额、原始核对、补回与未解决数量、结论和具体原因。
- `position_differences.csv`：34,437处差额逐笔证据，含前后记录编号、原始值、差额和规范化值。
- `missing_pnl.csv`：5,239笔仍缺官方PnL的记录，含来源和逐笔原因。
- `canonical_values.csv`：按原记录编号关联的派生值，不包含虚构成交。
- `source_receipts.json`：原档签名、解压内容SHA256及逐文件核对数量；原始文件和API响应留在本地。

## 恢复完整修复版 CSV

先用原结果目录的 restore_csv.py 还原原始完整CSV，再运行（Python 3.11+）：

```sh
python rebuild_audited_csv.py --input-csv 原始完整.csv --output 修复复核版.csv
```

工具验证输入、修复表和输出SHA256，不覆盖已有文件。完整输出保留387,726笔成交和4条诊断，原43列每个单元格均与旧版完全相同，追加7列。需要修复后的结论时读取“复核后轨迹完整性”和“复核后PnL完整性”，原完整性列特意保留原判断以便审计。
