## 均价计算与边界

本地 node_fills_by_block 保存成交 `px`、`sz`、`startPosition` 和 `closedPnl` 等字段，没有直接的历史持仓 `entryPx`。从零仓位开仓，或从穿零反向成交的剩余新仓位开始，沿同一用户、币种的成交重放：同向加仓按数量加权，减仓保持均价，全平归零。数量采用 Decimal 精确衔接，同毫秒采用原生流顺序或唯一可证明的数量链；不以成交 ID 大小猜测先后。主均价还要求开仓起点至接管时刻具备连续的可用来源时间覆盖，避免遗漏净数量为零的中间往返交易。

重建值是依据观察到的成交链计算的理论成本，未声称读取了原生账本 entry notional 或当时界面的历史 entryPx。近期 WebSocket 快照只补充成交，不单独证明某段历史完整；空接口回执也不证明更早成交不存在。只采用已完整导入的接口回执作为时间覆盖依据，排除已知错时或被替换的旧 ZIP 名义小时覆盖。可用来源的时间覆盖仍不能证明提供方从未遗漏记录。缺起点、数量断链、顺序不唯一、时间覆盖不足和来源冲突均保留空值。使用局部 60 位 Decimal 精度，不改变调用方 Decimal 上下文。

被接管方全平记录均经身份、币种、毫秒时间、哈希、价格、数量和反向平仓方向匹配。零手续费全平时，单独计算 `执行价 - closedPnl / (方向符号 × 平仓数量)`。该隐含值和成交链理论成本之间的所有差异均保留；差异不用于设置匹配容差，也不据此认定原生账本成本。隐含值没有覆盖主均价，HLP 收到仓位一侧的 PnL 没有用于反推用户成本。

## 来源、复核和使用

已复用本地目标小时完整成交、主要 2025-10-10 接管群缺口账户此前一个月的完整小时和旧账户的开仓生命周期，并交叉核验全部 16,431 个用户的官方近期成交快照。在已知开仓起点与接管时刻之间补读可信原档；缺起点的账户再向既有连续范围之前扩展 30 天，断链账户检查此前 30 天的缺口，并补查同毫秒原生顺序。另完整补读三个剩余旧格式账户所需的 1,309 个本地小时，通过精确成交指纹匹配补充顺序或缺失记录，避免重复计入 API 已有成交。

对 API 新发现的成本链时间缺口和同毫秒顺序问题，又按所需账户与时间补读本地原档。各批小时数、跳过数、新增记录数和读取错误数保存在核验证据中。

REST 历史查询按返回条数权重限速；WebSocket 使用单连接、单请求在途，并沿用按实际响应条数计算的保守权重节奏，在此前查询后优先核对 244 个已找到开仓起点的账户窗口，再对仍缺证据的 623 个账户执行所需历史窗口的分页查询。已由连续成本链核验的账户跳过后续查询。断链记录的补查从已观察到的零仓位或反向开仓时间开始；没有此类重置点的记录从接口可用历史开头查询。这个起点只界定修复查询的范围，不表示成本链已恢复。官方文档说明每次最多 2,000 笔，并称仅提供最近 10,000 笔；实际覆盖和每个查询窗口 20 页的任务限制记录在 [核验证据](victim_price_validation.json)。保留范围、分页上限和本轮尚未覆盖的更早窗口均不能解释为“没有历史”。已由本地成交链核验的账户不要求再查询完整接口历史，因此账户级 `not_started` 不等于价格缺失；未补齐行所需窗口的状态另行记录。没有请求 AWS、购买接口或升级套餐。

尚未补全的数量断链行附有最近已读断点的 UTC 时间、上一笔推算仓位、实际 startPosition 和精确差值。其中 5 处可由 binary64 加减精确复现；这仅用于诊断表示差异，不是提供方实现的证明，也不作为容差或改写原记录的依据。

官方规则与字段参考：[开仓均价与 PnL](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/entry-price-and-pnl)、[用户成交接口](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint)、[清算](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/liquidations)。

CSV 使用 UTF-8 BOM、CRLF；精确 SHA256、数量和接口范围见核验证据。离线逐格复核：
